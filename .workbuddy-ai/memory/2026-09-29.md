## 设备抽象 / 多型号接入的架构评估（只读分析，未改代码）

用户提出：希望前端不只服务 PXLogic，将来能对接其他型号逻辑分析仪，问「如何重构 + 是否值得重构」。
本次只做了代码勘察与评估，**没有修改任何源码**。

### 勘察结论（供后续复用）

耦合点只有 3 处，且是"硬编码"而非架构性绑定：

1. `src-tauri/src/main.rs`（2,116 行）—— `list_devices()` 硬编码 Fake + `RusbBackend::default()`；
   `device_capabilities()` 里 `if device_id == FakeBackend::DEVICE_ID {…} else { resolve_pxlogic_device_profile(…) }`；
   `RusbBackend::default()` 在 4+ 处临时 new；`prepare_real_device_cached` 直接调 `RusbBackend::load_bitstreams()`。
2. `crates/pxlogic-core/src/pxview_profile.rs`（762 行）—— `PXLOGIC_DEVICE_PROFILES: &[PxlogicDeviceProfile]`
   静态表，`&'static str` 字段；已含 4 型号 × 2 USB 速率共 10 条 profile。
3. `crates/pxlogic-core/src/transport.rs`（39 行）—— `CaptureBackend` trait 存在，但
   `prepare_device(device_id, bitstreams)` 把 FPGA bitstreams 泄漏进通用签名。

已经干净的层（重构成本低的原因）：

- `HardwareCaptureCapabilities`（`crates/pxlogic-core/src/models.rs`）**本身就是一份设备描述协议**：
  `max_channels / default_channel_count / sample_rates / threshold_volts / channel_modes[]`。
- 前端 `src/lib/api.ts` 的 TS 类型与它一一对应，通道数全部来自 capabilities/metadata，**没有硬编码 32**。
  品牌字符串仅约 10 处（`App.tsx:4940/8403` 的 logo 文案、`App.tsx:8202-8203` 的 "PXView Profile" 标签、
  `api.ts:1027-1034` 的 demo 设备名、`preferences.ts`/`extensions.ts` 的 localStorage key 等）。
- `crates/pxlogic-graph` 图内核按 `metadata.channel_count` 遍历，唯一限制是 `lib.rs:31 const MAX_CHANNELS: u8 = 32`。
- `DecoderBackend` / `DecoderBackendKind` / `DecoderBackendInfo`（`crates/pxlogic-core/src/decoder_backend.rs`）
  **已经是一套完整的插件协议范式**，含 `DecoderBackendIsolation::Sidecar` 进程隔离 —— 设备层可直接照抄。

### 关键事实（影响判断）

- `vendor/pxview-sigrokdecode` 只含 **libsigrokdecode**（解码库），**不含 libsigrok**（设备/传输库）。
  即：项目已复用 sigrok 的解码生态，但**尚未**复用其 ~100+ 设备驱动。这是多厂商接入的最高杠杆缺口。
- `docs/reuse-vs-rebuild-decision.md` 记录了 Saleae 官方文档原话：
  extension API "does not open how data arrives. There is no device, transport, importer,
  trigger, or UI extension point at any layer." → 业界标杆**刻意不开放设备层**，是最强反证。
- `App.tsx` 11,159 行单体；`docs/FILE_MAP.md` 已把它列为"工作台主体"。
  开放生态会让这个单体成为第三方贡献的实际障碍（无处安放设备配置 UI）。

### 给出的建议

分三阶段：Stage 0 品牌/命名外提 → Stage 1 补缝（`DeviceDriver` trait + `DeviceRegistry`，
去掉 `main.rs` 的 if/else，bitstreams 移出通用签名）→ Stage 2 清单 + sidecar 驱动
（照抄 `extension.json` 与 sidecar 模式）→ Stage 3 生态。
结论：**Stage 0+1 值得做**（收益由"支持自家 4 个型号"驱动，非假想第三方）；
**Stage 2+3 是商业判断**，建议等有 2-3 个真实第三方意向再做协议设计。
替代路线：直接接 libsigrok 设备层（GPL，需沿用现有 GPL sidecar 隔离模式），
优于自创插件协议。

已建议用户：是否把该评估落成 `docs/device-extension-architecture-decision.md`（本轮未创建）。

## 第二轮：实现方案与语言选择的代码级验证

用户认可架构图，追问"如何实现、用什么语言"。又勘察出两个决定实现方案的关键事实：

### 事实 A：稀疏转移格式已是现成的设备无关契约（重大利好）

- `crates/pxlogic-graph/src/lib.rs:360 DigitalGraph::from_sparse_capture(&SparseCaptureData)`
  已存在；`SparseCaptureData { channel, initial_high, transitions: Vec<u64> }` **与通道数无关**。
- 真实硬件路径已经在用它：`src-tauri/src/main.rs:770 GraphSession::replace_sparse_capture`。
- 唯一挡住外来设备的是 `crates/pxlogic-graph/src/lib.rs:4722 validate_metadata()` 的两条硬校验：
  1. `channel_count ∈ 1..=32`（`MAX_CHANNELS`，lib.rs:31）
  2. `unitsize == ceil(channel_count/8)`，即只允许 1/2/4
- 而 `unitsize` 在**稀疏路径上只被声明、从不被读取**（`from_sparse_capture` 不读打包样本）。
- `crates/pxlogic-core/src/capture.rs:293 unitsize_for_channel_count()` 与
  `:1386 read_sample_word()` 同样只接受 1/2/4 字节。
- **结论：放开的成本 = 改一个校验函数 + 加 SampleFormat 标签，不是重写。
  驱动只需产出"转移索引"，不需产出"打包样本"——驱动实现难度下降一个数量级。**

### 事实 B：`CaptureBackend` trait 目前是摆设，真实路径绕过它

- `crates/pxlogic-core/src/transport.rs` 的 trait 只有 5 个方法
  （`list_devices` / `prepare_device` / `capture` / `capture_streaming` / `stop_capture`），
  **且 `capture_streaming` 只吐打包样本字节，没有稀疏变体**。
- 真实路径走的是 `RusbBackend` 的**非 trait 方法**：
  `prepare_device_with_trace`(:334) / `configure_pwm0_with_trace`(:392) /
  `capture_with_trace_streaming`(:442) / `flash_mcu_firmware_with_trace`(:245) /
  `load_bitstreams`(:196)。`impl CaptureBackend for RusbBackend` 在 :1696 只实现了那 5 个泛型方法。
- **结论：任何设备扩展工作必须先让真实路径"穿过 trait"，否则抽象是装饰性的。**

### 给出的实现方案要点

- 语言：宿主与契约层保持 **Rust**；**不给第三方进程内 ABI**（Rust 无稳定 ABI，
  进程内 Rust cdylib 会强制第三方锁定 rustc 版本）；驱动一律 **sidecar 进程 + 版本化线协议**。
- SDK 优先级：**C ABI 头（通用底座）> Python（最低门槛）> Rust（一等公民）**。
- 三个面：元数据面（`device.json`，无代码）/ 控制面（NDJSON over stdio，低频）/
  数据面（共享内存环形缓冲，**搬转移索引而非样本**，SPSC 无锁 + 空闲水位背压）。
- 降级模式：慢设备（< ~10 MS/s）可完全不走共享内存，直接控制面推 block
  → 让业余设备驱动能用约 50 行 Python 写完。
- 进程外的三条硬理由：Rust 无稳定 ABI、驱动能直接操作 USB（崩溃/抢设备，比 HLA 更危险）、
  GPL 的 libsigrok 只能放进程外（沿用 `native/sigrok-analyzer-sidecar` 先例）。
- 新增 crate 规划：`pxlogic-device`（trait/registry/sidecar/ring）、
  `pxlogic-device-pxlogic`（从 core 迁出 PXLogic 专属）、`pxlogic-device-sigrok`、
  `sdk/device-driver-c`、`sdk/device-driver-python`、`docs/device-driver-spec.md`。
- 验收：Python 假设备（1 MS/s / 8ch）能进设备列表→采集→解码；
  32ch×50MHz 真实路径无回归（用现成 `pnpm perf:self-test`）；杀掉 sidecar 主程序不崩。

## 第三轮：纠正我自己的两个错误（用户追问"JSON IPC 指什么"）

用户质疑上一轮"采集热路径不能走 JSON IPC"的说法。核对代码后，**我错了两次**，必须记录以免复用：

### 错误 1：术语不准 —— 解码 sidecar 协议根本不是 JSON

`crates/pxlogic-core/src/decoder_backend.rs:519-522` 定义的是分帧二进制协议：
`SALEAE_FRAMED_BINARY_TRANSPORT = "framed_binary_v1"`，magic `PXLF1`，
header 上限 64 MB，blob 上限 2 GB。
写出是两段（`:2181-2182`）：`write_all(&request.json)` 然后 `write_all(&request.binary)`。
二进制体是 **delta-varint 编码的转移索引**（`encode_delta_varint_samples`，`:293`），
JSON 头里只放 `{offset,length}` 切片引用。
实现方式：`NativeEdgeSet` 自定义 `Serialize`（`:271`）在序列化时把样本数组
**分流到 thread-local 缓冲** `SALEAE_REQUEST_BINARY`（`:268`），不进 JSON。

### 错误 2：`0.41%` 的含义被我说错了，且数字夸大约 4–30 倍

- `docs/perf-attribution-2026-09-22.md:45-48` 的 0.41% **只覆盖 JSON 头**：
  `batch_request_json_encode` 0.251 ms + `persistent_batch_response_json_parse` 0.021 ms。
  **数据搬运不在这个数字里**：`persistent_request_write` 3.35 ms(5%)、
  `persistent_response_read` 54.32 ms(82%) 是分开的 stage，且后者主要是**等 sidecar 算**
  （与 `sidecar_execute` 62.72 ms 高度重叠），不是传输慢。
- 我说的"32ch × 500MHz ≈ 16 Gbit/s 跨进程"是**采样侧**速率。
  跨进程真正要搬的是 **USB 读出率**：`crates/pxlogic-core/src/capture.rs:405
  pxview_capture_transfer_size()` 里 USB2 建模为 `480_000_000/100/8` = **600 KB / 10ms = 60 MB/s**，
  USB3 单次传输上限 `4 MB`。按 10ms 分块推算，SuperSpeed 各模式的稳态约 **200–250 MB/s**。
  **真实量级是 60–250 MB/s，不是 2 GB/s。**

### 依然成立的部分

- 采集 raw data **今天根本不跨进程**：`src-tauri/src/main.rs:578/610` 的回调直接
  `append_samples(chunk)` / `append_cross_lanes(...)`，进程内零序列化。
- 解码器拿到的**不是原始样本**，是转移索引。
- 结论方向不变但风险等级下降，而且**项目已有现成答案**：
  设备驱动的数据面应复用 `framed_binary_v1` 的「JSON 头 + 二进制 blob」分帧约定，
  而不是新发明协议。进程边界的真实成本不是序列化，而是**拷贝次数**
  （stdio pipe 2 次拷贝 vs 共享内存 0–1 次），所以共享内存仍是正确选择，
  但理由是"少一次拷贝 + 背压可控"，不是"JSON 太慢"。

**教训：引用性能数字前必须确认该数字的 stage 定义覆盖范围，不能把"某阶段的一部分"说成"整条链路"。**

### sigrok 统一 87 种硬件的五层

1. **`sr_dev_driver`**（公开 vtable，14 个函数指针）：
   `name / longname / api_version / init / cleanup / scan / dev_list / dev_clear /
   config_get / config_set / config_channel_set / config_commit / config_list /
   dev_open / dev_close / dev_acquisition_start / dev_acquisition_stop / context`
2. **`sr_dev_inst`**（公开头文件中**不透明**，定义在 `src/libsigrok-internal.h`）：
   `driver / status / inst_type / vendor / model / version / serial_num /
   connection_id / channels / channel_groups / conn / priv / session`
3. **`sr_channel`**：`sdi / index / type(SR_CHANNEL_LOGIC…) / enabled / name / priv`；
   **`sr_channel_group`**：`name / channels / priv`（通道组共享属性，如 MSO bank 阈值）
4. **配置键值接口**（统一 87 种异构设备的真正关键）：
   `config_get/set/list(uint32_t key, GVariant **data, sdi, cg)` +
   `enum sr_configkey`（约 150 个 `SR_CONF_*`，横跨 LA/示波器/万用表/电源/电子负载/LCR/信号源）
   + 能力位 `SR_CONF_GET|SET|LIST`（`enum sr_configcap`）。
   `hwdriver.c:720 check_key()` 用 `SR_CONF_DEVICE_OPTIONS` 列表 + 能力位做**运行时校验**。
   元数据表 `sr_key_info_config[]`（`hwdriver.c:49`）提供 id/name/datatype 供 UI 用。
5. **`sr_datafeed_packet`** + `enum sr_packettype`（`SR_DF_HEADER/END/META/TRIGGER/LOGIC/
   FRAME_BEGIN/FRAME_END/ANALOG`）。`session.c:1124 sr_session_send()` 先过
   **transform 链**再分发给所有 datafeed callback。

**生命周期（两阶段，配置先攒后提交）**：
`init(ctx) → scan(options) → sr_dev_inst[] → dev_open → config_get/set/list →
config_commit → dev_acquisition_start → datafeed 包 → dev_acquisition_stop → dev_close → cleanup`

### 重大发现：sigrok 的设备驱动是编译期静态链接，无运行时插件

- 注册宏 `SR_REGISTER_DEV_DRIVER(name)`（`internal.h:1202`）把指针放进链接段
  `__sr_driver_list`（macOS 为 `__DATA,__sr_driver_list`，`internal.h:1131`）；
  `drivers.c` 用 `sr_driver_list__start` / `__stop` 迭代。
- **已验证 `dlopen` / `g_module_open` / `LoadLibrary` 在 `hwdriver.c`、`drivers.c`、
  `backend.c` 中出现 0 次。**
- 87 个驱动全部显式列在顶层 `Makefile.am` 的 `libsigrok_la_SOURCES`，用 `if HW_XXX` 条件编译。

→ **三个生态的数据点**：Saleae 明确不开放设备层；sigrok（87 驱动）抽象干净但**无运行时插件**，
必须合入上游重编译；pxlogic 目前硬编码 1 个设备族。
**结论：成熟栈的设备层从来是"策展"而非"开放"，这是刻意的产品选择，不是技术限制。**

### 对 Rust trait 的映射结论

- **控制面抄 sigrok**：vtable 形状、两阶段生命周期、`commit` 先攒后提交、通道组、
  能力位协商（但用 Rust enum + serde 取代 `uint32_t key` + `GVariant`，
  类型安全且不再需要 `sr_key_info` 运行时元数据表 + `check_key` 校验器）。
- **数据面不要抄**：`struct sr_datafeed_logic { length; unitsize; data; }` 是 **packed samples**，
  与本项目正要摆脱的 `CaptureData{ samples: Vec<u8>, unitsize }` 形状一致。
  应保留 `SparseCaptureData` 的转移索引模型 —— 这是 32ch 长采集的核心优势。
- **不要抄**：`api_version:int`（用 manifest `protocol_version` + 能力协商）、
  `void *priv`/`void *conn`（用关联类型）、`GSList`/`gboolean`/手动内存管理、
  全局扁平 `SR_CONF_*` 枚举、**进程内运行**（延续 `DecoderBackendIsolation::Sidecar`）。
- **最大杠杆**：sigrok 的 vtable 与本项目需要的 Rust trait 几乎 1:1 对应，
  因此写**一个** `libsigrok` 适配器即可一次性接入 87 个驱动（不是 87 个适配器）。
  libsigrok 是 GPL → 该适配器必须放 GPL sidecar（沿用 `native/sigrok-analyzer-sidecar` 先例）。

已产出 Rust trait 草案（`DeviceDescriptor` / `OptionValue` / `OptionCaps` /
`DeviceDriver` / `OpenDevice` / `SparseSink`）在对话中，未落盘。

## 第十五轮：Stage 1 —— DeviceDriver trait + DeviceRegistry（已完成前半相）

### 新增 `crates/sigpilot-core/src/device.rs`

按 sigrok `sr_dev_driver` 的形状设计，三处刻意偏离（已在模块文档里写明理由）：

1. **能力是类型化的** —— sigrok 用无类型 `uint32_t key` + `GVariant`，因此需要运行时
   键元数据表 + `check_key()` 校验器；这里直接用 `HardwareCaptureCapabilities`，类型错误变成编译错误。
2. **隔离是显式声明的** —— 新增 `DriverIsolation::{InProcess, Sidecar}`。
   sigrok 驱动永远在宿主进程内，坏驱动会崩整个应用；本项目沿用解码器侧
   `DecoderBackendIsolation::Sidecar` 的决定，把"第一方进程内 / 第三方进程外"放进 descriptor。
3. **只覆盖枚举 + 能力解析 + 生命周期** —— 捕获热路径**有意排除**（见下）。

**trait 表面**：`descriptor()` / `list_devices()` / `capabilities(id)` /
`prepare(id, sink)`（默认空）/ `stop(id)`（默认空）/ `invalidate(id)`（默认空）/
`owns_device(id)`（默认按 device-id scheme 路由）。

**`DeviceRegistry`**：`new()`（拒绝 scheme 冲突）/ `with_builtin_drivers()` /
`list_devices()`（容错：单个驱动失败不掩盖其他）/ `driver_for()` / `capabilities()` /
`prepare()` / `stop()` / `invalidate()`。

**device-id 路由**：`<scheme>:<rest>`，如 `fake:sigpilot-demo`、`usb:1a86:5237:1:4`。
**scheme 必须跨驱动互斥**（`new()` 会拒绝冲突）。已文档化：PXLogic 驱动目前独占 `usb`，
第二个 USB 驱动到来时需要厂商前缀 scheme（如 `usb-pxlogic`）。

## 第十九轮：修复设备名冗长（启动页 label vs cyme）

### 根因（已定位）

`crates/sigpilot-core/src/rusb_backend.rs` 的 `list_devices()` 里，label 的构造是：

```rust
let label = if let Some(profile) = identity.profile {
    format!("{} {} {vid:04x}:{pid:04x} bus {bus} addr {address}",
        profile.vendor, profile.model)      // ← 硬编码档案表
} else { ... };
```

- `profile.vendor` / `profile.model` 来自 `pxview_profile.rs` 的**静态表**
  （`PXLOGIC_DEVICE_PROFILES`，值为 `"PX_Tool"` / `"PX-Logic U3 channel 32"`），
  **不是设备上报的**。
- 后面还拼了 `{vid:04x}:{pid:04x} bus {bus} addr {address}` 调试信息。
- 用户截图里的 `16...` 就是 `16c0:05dc` 被截断（对应 cyme 的 `0x16c0 0x05dc`）。

**关键**：`probe_usb_identity()`（同文件 :1360-1362）**早就读了设备真实字符串**：
`read_manufacturer_string_ascii` / `read_product_string_ascii` / `read_serial_number_string_ascii`，
甚至用 `manufacturer` 做身份校验（要求以 `"PX"` 开头，:1364-1372）。
但这些字段只进了 `DeviceInfo.manufacturer` / `.product` / `.serial_number`，**没进 label**。

### 修复

`rusb_backend.rs` 新增 `fn device_label(identity, vid, pid)`，优先级：
1. 设备的 `manufacturer` + `product`（trim 后非空）→ `"PX USB3.0 Logic 32"`
2. `product`（无 manufacturer）
3. 档案表 `profile.vendor` + `profile.model`
4. `"PXLogic USB {vid:04x}:{pid:04x}"`

VID/PID/bus/addr **从 label 移除**（它们是调试信息，不是设备名）。

**前端**（`DeviceStartScreen.tsx`）：新增 `deviceLocation(device)`，
把 bus / address / 序列号放进行的 `title` tooltip —— 两台同型号设备仍可区分，信息不丢。

### 验证

- `cargo test --workspace` ✅ **218 passed / 0 failed**（新增 2 个 `device_label` 测试：
  优先设备字符串、以及 product→profile→IDs 的降级链，含空白字符串不得产生纯空格 label）
- `cargo check --workspace --all-targets` 无错误无警告

### 🐛 tsc 抓到的真实 bug（若不修，用户构建会失败）

```
src/components/DeviceStartScreen.tsx(152,44): error TS2322:
Property 'title' does not exist on type 'UsbSpeedIconProps'.
```

**根因**：`React.SVGProps<SVGSVGElement>` **不包含 `title` 属性** ——
`SVGProps` = `SVGAttributes & ClassAttributes`，而 `SVGAttributes` 继承
`AriaAttributes, DOMAttributes`，**不继承 `HTMLAttributes`**（`title` 在后者里）。
我在 `DeviceStartScreen.tsx` 传了 `title={usbSpeedLabel(usbSpeed)}`，类型不通过。

**修法**：`UsbSpeedIcon` 显式声明 `title?: string`，并渲染为**嵌套 `<title>` 元素**
（SVG 原生的 tooltip 机制），而不是当作属性透传。

→ **教训：`<img src="*.svg">` 与内联 SVG 的 prop 类型不同；给 SVG 加 tooltip 要用
嵌套 `<title>`，不是 `title` 属性。这类错误只有跑 tsc 才能发现。**

### 🐛 本轮第二个真实 bug：feature 门控下的 `unused_mut` 警告

跑 `pnpm perf:self-test` 时 stderr 暴露：

```
warning: variable does not need to be mutable
  --> crates/sigpilot-core/src/device.rs:187
```

**根因**：`sigpilot-graph` 依赖 `sigpilot-core` 时用了 `default-features = false`，
所以 `rusb-transport` 关闭 → `with_builtin_drivers()` 里那句
`#[cfg(feature = "rusb-transport")] drivers.push(...)` 被编译掉 → `let mut` 变多余。

**为什么之前没发现**：`cargo check --workspace` 用的是**默认 feature**（开启），
所以只查默认配置会漏掉这类问题。

**修法**：改成单表达式 + 元素级 `#[cfg]`，两种配置下都不需要 `mut`：
```rust
let drivers: Vec<Arc<dyn DeviceDriver>> = vec![
    Arc::new(crate::fake::FakeDriver::new()),
    #[cfg(feature = "rusb-transport")]
    Arc::new(crate::rusb_backend::PxlogicDriver::new()),
];
```

→ **教训：改了带 `#[cfg(feature)]` 的代码后，必须在 feature 开/关两种配置下都跑一次
`cargo check --all-targets`。只查默认配置会漏。**
