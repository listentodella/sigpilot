## 新增设备支持：Kingst LA2016（真机验证通过）

### 设备事实（实测，非猜测）

- `LA2016` = **Kingst**（青岛金思特）16 通道 / 200MHz / 128MiB，USB 2.0 High Speed
- **VID:PID = `0x77a1:0x01a2`**，与 LA1016 共用
- 硬件：Cypress **FX2LP**（易失程序存储器）+ Altera **EP4CE6** FPGA + AT24C02 EEPROM + U10 认证芯片
- **未编程状态的关键特征**：`bcdDevice = 0.0.0`、接口 0 的 **alt 0 没有任何端点**、
  **`iManufacturer` / `iProduct` / `iSerialNumber` 全是 0（没有任何字符串描述符）**

### ⚠️ 踩到的两个坑（都靠真机才发现）

**1. 不能按 `iProduct` 过滤设备。** 参考驱动 `api.c` 里有
`des.iProduct != LA2016_IPRODUCT_INDEX(2)` 的检查，我照抄到了 `list_devices`——
结果**枚举到 0 个设备**。原因：那个常量用在**固件上传后的重新枚举**路径上，
而未编程的 FX2 根本没有字符串描述符（`iProduct = 0`），恰好把最需要处理的
「待编程」状态排除了。

**2. 必须 `claim_interface(0)`。** 不 claim 接口时，控制传输（EP0）能成功，
但**批量传输会返回 `LIBUSB_ERROR_NOT_FOUND`**——FPGA bitstream 走 EP2 bulk，
所以表现为「识别成功、烧 bitstream 失败：Entity not found」。
参考驱动 `la2016_open_usb` 里就是 open + claim，**不设 alt setting**（固件自己会切到 alt 1）。

### ① 采集路径（已实现并真机验证）

**协议要点**（全部来自参考实现，非猜测）：

| 项 | 内容 |
| --- | --- |
| 阈值 | `REG_THRESHOLD(0x68)` 写 `u16le duty_R56, u16le duty_R79`。分段公式：`v>=2.9` → R79=0x0000/R56=302v−363；`v>−0.4` → R79=0x00f2/R56=302v+121；否则 R79=0x02d7/R56=302v+1090。R56 钳在 [10,1100] |
| 采集模式 | `REG_CAPT_MODE(0x03)` 写 1 字节，0x00=存 SDRAM |
| 触发 | `REG_TRIGGER(0x20)` 写 16 字节（`u32le channels/enabled/level/high_or_falling`），**wValue=16**。全 0 = 不触发 |
| 采样配置 | `REG_SAMPLING(0x10)` 写 **16 字节**：`u40le 总数, u40le 预触发数, u24le(预触发内存>>8), u16le 分频, u8 0`。分频 = 基准时钟/采样率；**基准时钟 = model.samplerate**（LA2016=200MHz） |
| 启动 | `REG_RUN(0x00)` 写 1 字节 = 0x03 |
| 等待完成 | 轮询 `REG_RUN` 读 2 字节，bit0=1 即 idle |
| 采集信息 | **同一个 `REG_SAMPLING` 读** 12 字节：`u32le n_rep_packets, u32le 触发包索引, u32le write_pos`（读/写含义完全不同，厂商怪癖） |
| 下载 | `CMD_BULK_RESET(0x38)` → `REG_BULK(0x08)` 写 `u32le read_pos, u32le n_bytes` → `CMD_BULK_START(0x30)` → 读 **EP 0x86** bulk IN |
| **包格式（16 通道）** | 每 transfer **16 字节** = **5 × (`u16le pins` + `u8 重复数`)** + **1 字节序号**。32 通道：32 字节 = 6 × (`u32le` + `u8`) + 2 序号 |
| 传输参数 | `packets_per_chunk = (transfer_size − sequence_size) / (unit_size + 1)` → 16ch=5，32ch=6 |
| 样本转换 | **每个包的值重复 `重复数` 次**。16 通道的 `u16` 引脚值**就是** SigPilot 的 2 字节样本字（`unitsize_for_channel_count`：9..=16 → 2），所以直接展开即可，无需位序变换 |

**实测（LA2016，1MHz × 20ms = 20000 样本）**：
```
threshold 3.3V: 20000 samples in 29.8ms, 1 distinct, 0 transitions
  requested 20000  payload 40000 bytes  consistent true
  raw download 256 bytes (~250.0 samples/packet; 255 = fully compressed)
```

**决定性证据是压缩比**：20000 样本只下载 **256 字节**（80 个包 × 约 250 重复），
即 **RLE 接近 250:1**。**数据通路若是坏的，不可能产出这种压缩比**——那要求 FPGA
真的连续采了 20000 个样本并写入 SDRAM。所以：固件上传、识别、FPGA bitstream、
配置、启动、等待、下载、RLE 展开、格式转换**每一环都验证为工作**。

**未能验证的**：样本值全 0，且换阈值（3.3V/1.2V）结果相同。**台面上输入未接线**，
所以无法区分「输入无信号」与「模拟前端有问题」。要闭环需要给通道接一个已知信号
（或把设备自己的 PWM 输出跳线到某个通道输入——PWM 在独立引脚，无内部回环）。
**不要把这个当作"数据正确"来宣称。**

## 🎯 根因找到并修复：`REG_TRIGGER` 的第一个 u32 是「启用通道掩码」，不是触发字段

用户加强地线后仍全零。继续排查，最终在参考实现的 `set_trigger_config` 开头发现关键代码：

```c

cfg.channels = devc->stream.enabled_mask;
if (!cfg.channels) {
    sr_err("Need at least one enabled logic channel.");
    return SR_ERR_ARG;          // ← 参考实现会在这里直接报错退出
}
```

结构体注释写得很清楚：
```c
struct trigger_cfg {
    uint32_t channels;         /* Actually: Enabled channels? */
    uint32_t enabled;          /* Actually: Triggering channels? */
    uint32_t level;
    uint32_t high_or_falling;
} cfg;
```

**`REG_TRIGGER` 的第一个 `u32le` 是「启用通道掩码」。我原来把 16 字节全写 0 —— 等于告诉设备「一个通道都没启用」，所以采到全零。** 参考实现遇到这种情况会报错，我的代码静默写入了 0，于是表现为「采集成功但数据全零」，**看起来和接线故障一模一样**，害我排查了很久。

掩码计算抽成 `enabled_channel_mask()` 并加了回归测试（注释里写明这个坑）。

## 修复客户端报错「capture metadata is invalid」

用户在客户端选 LA2016 点捕获，报这个错，看不到任何波形。

### 根因：我的 metadata 自相矛盾

- **`unitsize` 取自设备型号**（LA2016 是 16 通道 → `layout.unit_size = 2`，固定）
- **`channel_count` 取自调用方请求**（`settings.channel_count`）

而前端会话的默认通道数是 **8**（`src/App.tsx:572`；`src/lib/api.ts:1090` 的预览能力也是
`max_channels: 32, default_channel_count: 8`）。

`crates/sigpilot-graph/src/lib.rs:4722` 的 `validate_metadata`：

```rust
let expected_unit_size = match metadata.channel_count {
    1..=8 => 1, 9..=16 => 2, 17..=32 => 4, _ => unreachable!(),
};
if metadata.unitsize != expected_unit_size || metadata.sample_rate_hz == 0 {
    return Err(GraphError::InvalidMetadata);   // ← "capture metadata is invalid"
}
```

→ 我报 `channel_count=8` + `unitsize=2`，校验要求 8 通道必须是 1 字节 → 直接被拒。
`begin_capture` 里 `DigitalGraph::new(metadata)` 就是抛出点。

### 修复

**LA 系列没有窄采集模式，永远采全部通道**。所以 metadata 必须报**设备宽度**，
调用方想要的子集通过 `enabled_channels` 表达：

```rust
let channel_count = model.channels;                      // 而不是 settings.channel_count
let enabled_channels = resolve_enabled_channels(channel_count, &settings.enabled_channels)?;
```

`labels` 也改成按 `channel_count` 生成。

### 流式模式已实现（`CAPTMODE_STREAM`）

**协议要点**（来自参考实现，非猜测）：

| 项 | 内容 |
| --- | --- |
| 布局 | **每个 `u16le` 实体 = 一个通道的 16 个连续样本**，**bit0 最早**。按启用通道顺序遍历，禁用通道不占空间 |
| 块 | 所有启用通道各出一个实体后，组装出 16 个样本：样本 n 由各通道实体的 bit n 组成 |
| 每块字节数 | `启用通道数 × 实体大小`（16 通道设备实体 2 字节，32 通道 4 字节） |
| 启动时序 | `CMD_BULK_RESET(0x38)` → `set_run_mode(RUN=0x03)` → `CMD_BULK_START(0x30)`，**三者必须紧挨着**（参考实现注释：中间有停顿会让流卡住，因为 FX2 FIFO 会溢出） |
| 停止 | `set_run_mode(HALT=0x00)` |
| 空传输 | **超时是合法的**（设备慢或未触发），不能当错误 |

实现要点：
- `StreamLayout` + `StreamParser`（跨 chunk 保留 `channel_index` 和 `sample_data`，
  因为 USB 读不会落在块边界上——参考实现同样如此）
- `expand_stream_chunk()`，输出直接是 SigPilot 的 packed 格式
- `capture()` 新增 `cancel: &AtomicBool` 参数，`duration_ms == 0` 表示「直到取消」
- 停止时**无论哪条路径都发 HALT**，否则设备会继续往没人读的 FIFO 里灌

### ⚠️ 关键发现：USB 2.0 带宽是硬限制

**200MHz × 16 通道 = 3200 Mbps**，而 USB 2.0 High Speed 只有约 480Mbps。
表现是**采集极慢（几乎挂住）**，而不是报错——设备节流 + 丢样本。

参考实现有 `LA2016_STREAM_MBPS_MAX = 200` 的警告阈值，我加上了等价检查，
**走 `diagnostics` 通道而不是 `tracing`**（因为 bins 没装 subscriber，`tracing` 输出会丢；
app 里才装）。实测：

```
[Warn] streaming 200 MHz across 16 channels needs about 3200 Mbps, more than USB 2.0 can
       carry; the device will throttle and drop samples. Lower the sample rate, enable fewer
```

**1MHz × 16 通道 = 16 Mbps** 下流式正常：一次 512KB 读就完成，380ms 内采到 20000 样本 ✓

## 修复「流式仍只出 10ms」：截断没按模式区分

日志铁证：

```
01:48:52.641  start_capture ... mode=Stream  duration_ms=10
01:48:55.381  capture finished  sample_count=200000     ← 跑了 2.74 秒
```

2.74 秒却只返回 **200,000 样本 = 10ms × 20MHz**，正好是 `duration_ms` 的量。

**根因**：`capture()` 末尾的截断
```rust
if sample_count > 0 { samples.truncate(sample_count * unit_size); }
```
这段本意是处理 **buffer 模式**在包边界上的过冲（设备以包为界停止，最后一个包的重复数会超），
但**没有按模式区分**，把流式也截了。流式没有包边界问题，只由 `cancel` 界定。

已改为仅 buffer 模式生效。

### ⚠️ 但真正的瓶颈还在：流式吞吐量极低

同一份日志显示：2.74 秒只拿到 200,000 样本 ≈ **73k samples/s**，
而请求是 **20MHz**——**只有 0.4%**。

结合每读超时 500ms 推算：每次 `read_bulk` 大约只拿到 36k 样本（73KB），
而不是填满 512KB。**这就是「跑一小会儿就停」和「不实时」的真正原因**——
数据是涓流进来的，不是流进来的。

参考实现用 **8 个并发 512KB 异步传输池**喂满管道；我是**单线程同步读**，
读与读之间 FX2 FIFO 溢出 → 设备节流 + 丢数据。

## 修复拔插/重新枚举后无法采集（commit `5210798`）

### 根因

设备 id 内嵌 bus:address，**每次重新枚举都会变**：
- 上传 FX2 固件后
- 拔插后（FX2 掉固件 → 变成无端点状态）

`bring_up` 的回退链是：`open_device(旧 id)` 失败 → `prepared_device_id()`，
而后者**只接受已有端点的设备**。拔插后的设备没有端点 → 回退也失败 →
最后退回**过期的 id** → 后续 `open_device` 失败 → `no driver claims this device`。

**荒谬之处**：`bring_up` 的本职工作就是给无端点设备烧固件，却因为这个回退链做不到。

### 修复

新增 `KingstLa2016Driver::resolve_device_id()`：
1. 优先**已编程**设备（正在跑的那台）
2. 否则**任意** Kingst 设备——烧固件正是 `bring_up` 的职责

4 处调用点（`capture` + 3 个诊断入口）统一改用它。

**并让 metadata 回报「解析后」的 id**（而不是调用方传进来的），
这样前端一次采集后就自动采纳正确地址，**会话自愈**。

### 验证


`kingst_app_path` 新增 `SIGPILOT_STALE_ID` 环境变量以便复现该场景。

## 读块大小实测（commit `f1ada48` 回退到 32KB）

| 读块 | 速率 | 窗口 | 实际样本 | 理论值 | 达成率 |

### 诚实的结论：同步读撑不住长采集

- **短采集（500ms）能到 80~83%** ✓

且不是调参能解决的**——参考实现用 **8 个并发传输池**正是为此。

## 研究参考实现后的结论：必须做异步传输池（本轮未实现，先记录设计）

**用户问得很对：「是否有必要去学 sigrok 的驱动方法？它们总不至于只能捕获 30ms」——答案是必须，而且我该一开始就做。**
我一直在零散打补丁，没理解它的架构。

### 参考实现的架构（`protocol.c`）

```
LA2016_USB_BUFSZ      = 512 KiB   ← 每个传输的缓冲
LA2016_USB_XFER_COUNT = 8         ← 池大小（共 4 MB）
```

- `la2016_usbxfer_allocate()`：分配 8 个 `libusb_transfer` + 各 512KiB 缓冲
- `la2016_usbxfer_submit_all()`：一次性提交 8 个异步传输
- `receive_transfer()` 回调：处理数据后**立刻重新提交同一个传输** → 管道永远有待处理的读
- **超时不是错误**：回调直接看 `transfer->actual_length`，空输入完全合法

### 为什么我的同步实现追不上

**同步 API 在超时时会取消传输并丢弃已收到的字节**（这是 `read_bulk` 的行为）。
所以 512 KiB 对我永远失败、对参考实现完全正常——**同一个尺寸，两种 API 的语义不同**。

我的实测：32KB 短窗口 80~83%，长窗口掉到 54%。每次 `read_bulk` 的
分配/提交/等待/回收开销就是那 20~45% 的缺口，**读线程也修不了**。

### 阻塞点与可行路径

- **rusb 0.9.4 不暴露异步 API**（无 `transfer.rs`，无 `libusb_submit_transfer`）
- **但 `libusb1-sys 0.7.0` 已在依赖树中**（rusb 的底层），且自带完整 libusb 源码，
  异步符号可用 → **FFI 路径可行**

### 实施要点（下一轮）

1. 用 `libusb1-sys` 直接调 `libusb_alloc_transfer` / `libusb_fill_bulk_transfer` /
   `libusb_submit_transfer` / `libusb_handle_events_timeout`
2. 8 × 512 KiB 池，回调里重新提交
3. 缓冲所有权：`Box<[u8]>` + `Box::into_raw`，回调用 `user_data` 取回
4. 取消：`libusb_cancel_transfer` + 等所有回调返回后再释放
5. 需要 `unsafe`，必须仔细处理 transfer 生命周期

**这是一块真活，不能糊弄。** 上一轮若在几乎没上下文的情况下硬写 unsafe 代码，
风险大于收益——所以这轮只把设计定下来。
