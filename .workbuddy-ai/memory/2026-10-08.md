## 采集时长不稳定（几百 ms ~ 两三秒）——根因是读循环里的停顿

### 用户报告

1. 点击捕获后 LA2016 的波形时长不固定：有时几百毫秒，有时两三秒
2. 捕获期间**滚轮缩放不能正确作用，但键盘缩放可以**

### 决定性证据：流本身完全正常，是「猝死」

上轮加的 `capture_updated sample_count / graph_sample_count` 诊断终于给出答案：

```
capture_updated sample_count=44728320 graph_sample_count=44728320
...
capture_updated sample_count=63604736 graph_sample_count=63604736
capture finished sample_count=63604736
```

**两个数字完全一致且持续增长** → 后端发的计数是对的（上轮两个假设都被证伪是对的）。

再看时间结构（`STREAM_CHUNK = 32 KiB`，每 50.8 ms 一次更新，增量恒为 1,015,808）：

| 项 | 值 |
| --- | --- |
| 流速率 | **20.00 ~ 20.08 Ms/s**（请求 20 MHz）→ **零丢失** |
| 流持续 | 起采后 **4.28 s** 突然停止 |
| 之后 | 空等 `STREAM_STALL_TIMEOUT`（10 s）才结束 |

**不是带宽问题、不是渐进劣化**（有一次 04:47:09 拿到 97.5%），是**硬停止事件**。

### 根因：`samples` Vec 倍增重新分配 → 读循环停摆 → FIFO 溢出

`capture_streaming` 里 `let mut samples = Vec::new();` 无上限增长。
Rust 的 `Vec` 按倍增扩容，**每次扩容都要拷贝已有全部数据**。
采到几十 MB 时，一次拷贝要**几毫秒到几十毫秒**；这期间**没有任何 USB 读在飞**，
FX2 FIFO 溢出 → **设备停止发送**。

**确认方式：看各次采集停止时的数据量**

2.2 / 8.1 / 13.3 / 16.4 / 32.4 / 61.7 / 63.6 / 64.4 MB

**几乎都紧贴 2 的幂边界**，正是这种 `Vec` 的倍增点。太整齐，不可能是巧合。

### 第二处停顿：读循环里的同步 `emit`

`progress`（每 200 ms ×2）、`diagnostics`、`samples`（每 50 ms）三个闭包都直接在
读循环里调 `app.emit(...)`。`emit` 要序列化 payload 并投递给 IPC，
**webview 忙时耗时数毫秒** → 同样的 FIFO 溢出路径。合计约 30 次/秒。

### 修复（两个提交）

**`34251cb`** `SampleBlocks`：固定 **4 MB 块**累积，块内追加**永不搬移**已有字节，
结束时（设备已 halt，长拷贝不再威胁读循环）一次性展平。
另加 `worst read gap` 诊断——这是解释提前停止的关键数字，此前完全不可见。

代价是进度值晚一个 tick，不值得为它阻塞 USB 读。

## 回答「PXLogic 是否实现过异步传输池」——**没有**

### 核实结果

`crates/sigpilot-core/src/rusb_backend.rs` 的流式读循环（约 780 行）：

```rust
while bytes_read < target_raw_len {
    if cancel.load(...) { ... }
    match handle.read_bulk(data_endpoint, &mut buffer, read_poll_timeout) { ... }
}
```

**与我的实现同样是「单线程同步 `read_bulk` 循环」**，没有 `libusb_transfer`、
没有传输池、没有读线程。全文件搜 `thread::spawn|submit_transfer|pool` 均无相关结果。
→ **项目内没有异步池先例**，要做就是引入新东西。

### 但 PXLogic 有两处我该抄的东西（已抄，commit `bdd2089`）

**① 读尺寸由速率算出**（`crates/sigpilot-core/src/capture.rs:405` `pxview_capture_transfer_size`）

算法：**每通道 10ms 的数据量** → 向上对齐 4096 → × 通道数 →
受「USB 2.0 在 10ms 内能承载的量」约束（`480Mbps/100/8 = 600,000` 字节，对齐 4096）。

| 配置 | 算出的读尺寸 |
| --- | --- |
| 20 MHz × 8ch | **224 KiB** |
| 10 MHz × 8ch | 128 KiB |
| 2 MHz × 8ch | 32 KiB |

我原来用**固定 32 KiB**——在 20MHz 下只够 1.6ms，在 2MHz 下要 131ms。**固定值不可能对所有速率都对。**

**② 读超时是「轮询间隔」而非「截止时间」**：`capture_read_poll_timeout() = 250 ms`
（我原来是 1000ms）。因为读尺寸按 10ms 填满设计，250ms 已是 25 倍余量。

已复用 `pxview_capture_transfer_size`（crate 根已导出），超时改为 250ms。

### ❌ 但间歇性停流**没有改善**，数字说得很清楚

| | 3 次 10 秒 @ 10MHz × 8ch 的数据时长 |
| --- | --- |
| 固定 32 KiB（改前） | 2.46 s / 1.35 s / 8.52 s |
| 按速率算（改后） | 9.90 s / 1.55 s / 0.85 s |
| 按速率算 + 每次间隔 5s | 1.35 s / 6.68 s / 2.07 s |

**两组统计上无法区分**，加空闲间隔也无用 → 「设备需要恢复时间」的假设也被否掉。

**保留改动**：因为它由速率推导而非拍脑袋，且与其他驱动一致——**不是因为它有用**。

### 结论：异步传输池仍是唯一出路

| | 在飞缓冲 | 容忍的调度抖动 |
| --- | --- | --- |
| 参考实现（8 × 512 KiB） | 4 MB | ~100 ms |
| 我的（1 × 224 KiB @ 20MHz） | 224 KiB | ~11 ms |

注：**之前「32 KiB 最优、256 KiB 灾难」的结论不可靠**——每次只跑了一次，
而现已证实行为是随机的。以后改这类参数必须多次重复测量。

## 【关键】实测出 LA2016 的余量：**只有约 2 ms / 4 KB**

用户问「为什么 PXLogic 不需要异步池，同样 USB2 下也没这么难搞」。不猜，
加了 `SIGPILOT_KINGST_STALL_PROBE_MS` 探针（读循环里故意停一次），实测：

**10 MHz × 8ch（10 MB/s），5 秒窗口：**

| 停顿 | 结果 |
| --- | --- |
| 0 ms | 49,020,928 样本（窗口的 98%）✓ |
| 1 ms | 49,020,928 ✓ |
| 2 ms | 49,020,928 ✓ |
| **5 ms** | **2,048 样本 —— 流当场死亡** |
| 10 ms | 2,048 —— 死亡 |
| 20 ms | 2,048 —— 死亡 |

**2,048 样本 × 2 字节 = 4096 字节 = 正好是 FX2LP 端点缓冲上限（4 KB）。**

→ **设备的全部余量就是「一个端点缓冲」，约 4 KB / 10MB/s 下约 0.4 ms（实测能撑到 2 ms）。**
越过就永久停流，不会恢复。

**这解释了全部现象**：读与读之间几百微秒的间隙无所谓；任何更大的停顿
（OS 调度、缺页、GC）都会结束采集 → 所以是**随机的、无速率边界的**。

**也解释了为什么 PXLogic 不需要**：其设备是现代控制器（FX3 级），
有真正的 DMA 和大缓冲；而 `pxview_capture_transfer_size` 把单次读设计到
600 KB 在飞（10ms），本身就说明它有大缓冲可依赖。**LA2016 的 FX2LP 没有。**

### 对比

| | 设备侧缓冲 | 主机在飞缓冲 | 可容忍停顿 |
| --- | --- | --- | --- |
| LA2016（FX2LP） | **4 KB** | 1 × 224 KiB | **~2 ms** |
| 参考实现（8 × 512 KiB） | 4 KB | 4 MB | ~100 ms（把设备侧短板补上） |
| PXLogic 设备 | 大（DMA） | 1 × 600 KB | 本来就够 |

**结论：异步池不是「让 PXLogic 那样快」，而是「补上设备侧只有 4 KB 这个短板」。**

提交 `cb4d3d2`（探针保留，与 `SIGPILOT_STALE_ID` 同类，环境变量控制，正常运行不生效）。

## ✅✅ 异步传输池实现完成并验证（commit `356fa2a`）——间歇性停流**根治**

### 新增公共模块 `crates/sigpilot-core/src/bulk_in_pool.rs`

**刻意做成设备无关**（用户要求，便于将来接入其他型号）：
任何持有 `rusb::DeviceHandle` 且有 bulk IN 端点的驱动都能用，
调用方提供 endpoint / 传输尺寸 / 池深度，模块内不含任何逻辑分析仪概念。

API：
```rust
BulkInPool::start(handle, endpoint, transfer_size, depth) -> Result<Self>
pool.service(wait, &mut |chunk: &[u8]| -> Result<()>) -> Result<Delivered>
pool.stop()          // 幂等；Drop 也会调
pool.device_gone() -> bool
```

**关键技术点**：
- `rusb` 不暴露 libusb 异步 API → 走 `libusb1-sys`（rusb 本就链接的同一个 crate，`vendored` 共享）
- 超时的传输会通过 `transfer->actual_length` **保留已收字节**（同步 API 会丢弃）——这是第二个理由
- **所有权是难点**：缓冲用 `Box::into_raw` 交给 libusb，**必须等回调返回后才回收**，
  否则 libusb 会写已释放内存。取消后仍未回来的传输**宁可泄漏也不释放**（有界泄漏 ≫ UB）
- **全部在调用线程完成**（libusb 在事件处理内回调），无线程跨界、无 channel，样本天然有序
- `libusb_handle_events` 的 `LIBUSB_ERROR_BUSY`（另一线程在跑事件）按瞬态处理，sleep 后重试
- 回调内**不能 panic** → 用 `std::sync::Mutex` 并 `unwrap_or_else(|p| p.into_inner())`

依赖：workspace 加 `libc = "0.2"`、`libusb1-sys = { version = "0.7", features = ["vendored"] }`；
`sigpilot-core` 的 `rusb-transport` 特性扩展为 `["dep:rusb", "dep:libusb1-sys", "dep:libc"]`。

| 20 MHz | 0.06 ~ 1.20 s（**每次都失败**） | **9.89 / 9.90 / 9.89** s |

**三次运行完全一致（连样本数都相同）**，修复前相差 6 倍。20 MHz × 8ch 此前从未成功过。

| 项 | Kingst | PXLogic |
| --- | --- | --- |
| `channel_count` | **恒为设备宽度 16**（我刻意这么报，为满足 graph 的 unitsize 一致性） | 所选模式的宽度（如 8） |
| `unitsize` | **恒为 2** | 随通道数（8ch → 1） |
| 进图路径 | `append_samples`（普通 packed） | `append_cross_lanes`（cross-lane 打包） |
| 采集规模 | 20MHz × 10s ≈ **2 亿样本** | 通常小得多 |

**`channel_count` 恒报 16 是我引入的**——这是最可疑的一处，值得优先验证。

## ✅ 滚轮缩放根因找到并修复（commit `ed74159`）——**我的假设是错的**

### 日志给出了硬数据（前端日志通道第一次用就命中）

```
deltaY=1  wheelDeltaY=-3   factor=1.0015   ← 物理滚轮一格
deltaY=2  wheelDeltaY=-6   factor=1.0030
deltaY=3  wheelDeltaY=-9   factor=1.0045
deltaY=30 wheelDeltaY=-90  factor=1.046    ← 快速滚动（macOS 会加速）
```

**`wheelDeltaY` 在 WKWebView 里是存在的**——我上轮「WKWebView 没有这个属性」的怀疑**被证伪**。
Apple 文档说它 Deprecated（macOS 10.5–10.14），但运行时仍在。

### 真正的 bug：判据写成了 Chromium 的约定

```ts
// 旧代码
return wheelDeltaY !== 0 && Math.abs(wheelDeltaY % WHEEL_NOTCH_DELTA) === 0;  // 120
```

**WebKit 的约定是 `wheelDeltaY = -3 × deltaY`**（deltaY 是整数「行数」），
所以 `% 120` **永远不为 0** → **每一次滚轮都落到触摸板曲线** `exp(deltaY × 0.0015)`：

- 一格 `deltaY=1` → **1.0015 = 0.15%**，等于没动 ← 正是用户说的「有动作但不缩放」
- 快速滚动 `deltaY=30` → 4.6%，仍然很小

**也解释了「先用 WASD 放大后滚轮才稍微响应」**：同样的比例因子作用在更窄的跨度上，
像素位移更大，所以「看起来」有反应。

### 修复

新增 `wheelNotchUnit()`：同时识别两种约定——
- Chromium：`|wheelDeltaY % 120| === 0` → 每格 120
- WebKit：`deltaY` 为整数 **且** `|wheelDeltaY| === 3 × |deltaY|` → 每格 3

并且**对每事件的格数封顶 `MAX_NOTCHES_PER_EVENT = 3`**：macOS 会按滚动速度加速，
日志里出现过单事件 30/39/54 行——不封顶一次快滚就是 `2^15`。

### 测试

`tests/wheelZoom.test.ts`（模块此前**没有任何测试**），5 条覆盖两种约定 + 触摸板 + 捏合。
**第一版我把符号写错了**（以为 `factor > 1` 是放大）——代码注释写明 `factor < 1` 才放大，
**是测试错了，实现是对的**。这个「先怀疑自己的测试」的习惯再次奏效。

### 未解决

**「捕获停止后用滚轮常造成波形渲染异常」**——尚未定位。一个待验假设：
修复前每格只有 0.15%，用户会连续滚动多次，每次都发一个 intent + 重请求帧，
但视口几乎不动 → 帧循环空转 → 渲染异常。修复后每格 41%，这个churn 应消失。

**另外发现仓库里留着一处诊断残留**：`src/lib/wheelZoom.ts` 的
`ZOOM_ANIMATION_DURATION_SCALE = 0`，注释写着「TEMPORARILY 0 — diagnostic bisect」。

## ✅ 对齐官方客户端的通道/采样率关系（commit `b1b1de3`）

### 官方（用户从 Win 客户端读出）

| 模式 | 通道数 | 最高采样率 |
| --- | --- | --- |
| **Stream** | ch0~2（3） | **100 MHz** |
| | ch0~5（6） | **50 MHz** |
| | ch0~15（16） | **20 MHz** |
| **Buffer** | ch0~3 / ch0~7 / ch0~15 | **200 MHz**（与通道数无关） |

**规律**：`通道数 × 速率 ≈ 300~320 Mbps` —— 就是 USB 2.0 能承载的量。
参考实现的注释也明说：「Streaming mode is constrained by the channel count and
samplerate product（USB 上的比特率）」。

### 我们原来的两处错误

**① 速率表错了**：`while rate >= 1_000_000 { rates.push(rate); rate /= 10; }`
→ 只有 **[200M, 20M, 2M]**，漏了 100/50/10/5/1 MHz。
参考实现的表是 **1/2/5 步进**：`1, 2, 5, 10, 20, 50, 100, 200, 500`。
**`configure_sampling` 本来就能设任意 ≤ 基准时钟的速率**（100MHz 只需分频 2），
所以 100/50 MHz **一直可用，只是没在 UI 里列出来**。

**② Stream 模式只有一条通道模式**，`channels = 16` 且 `max = 200 MHz`，
**完全没有按通道数分档**。

### 修复

- `model_sample_rates(max)`：1/2/5 序列，降序
- `STREAM_BITS_PER_SECOND_MAX = 320_000_000`（从官方分档反推，不是抄表）
- `stream_channel_brackets(device_channels)` → `[3, 6, device]`（去重、不超设备）
- `stream_rates(model_max, channels)`：`min(型号上限, 预算/通道数)` 再取序列内最大可选项
- Buffer 一条（全速率、全通道数）✓ 与官方一致
- 运行时带宽警告阈值从 200 Mbps 改为同一个 320 Mbps 预算（否则 UI 允许的选择会被警告）

### 真机核对

```
KINGST_BUFFER16  16ch  200 MHz   stream=false
KINGST_STREAM3    3ch  100 MHz   stream=true
KINGST_STREAM6    6ch   50 MHz   stream=true
KINGST_STREAM16  16ch   20 MHz   stream=true
```

**与官方分档完全一致。** 前端 `sampleRateOptionsForCapabilities` 用
`cm.channels >= channelCount` 取匹配模式的速率**并集**，所以：
- 2 通道 → 匹配 3/6/16 → 最高 100 MHz ✓
- 4~6 通道 → 匹配 6/16 → 最高 50 MHz ✓
- 8~16 通道 → 匹配 16 → 最高 20 MHz ✓

3 条新单元测试固化这个对应关系（`offers_the_rates_the_hardware_actually_has`、
`streams_the_rate_the_vendor_client_streams_at_each_channel_count`、

2. **`max_sample_rate_hz` 一度报成 106/53 MHz**（预算的原始商，不是硬件的真实速率）——

## 滚轮「又异常」——**不是我新改的，是上一个修复过度校正**（commit `aa32b4a`）

### 先回答「你有没有改动」

`git diff --stat ed74159..HEAD -- src/ tests/` → **空**。
滚轮修复之后唯一的前端相关提交是后端速率表（`b1b1de3`，只动
`crates/sigpilot-core/src/kingst_la2016.rs`）。**我一行前端都没动。**

### 真正的原因：上轮修复把 deltaY 当成了格数

日志里一次手势的完整序列：

```
deltaY=1  → factor=1.414   ← 一格
deltaY=7  → factor=2.828   ← 夹到 3 格
deltaY=14 → factor=2.828
deltaY=22 → factor=2.828
deltaY=27 → factor=2.828
```

**macOS 会按滚动速度加速滚轮**，一次快滚 = 一串 deltaY 递增的事件。
我把 deltaY 当格数（还封顶 3），于是 **一次快滚 = 1.414 × 2.828⁴ ≈ 90 倍**。
比它要修的那个 bug（0.15%）还糟。

### 修正：**WebKit 下「一个事件 = 一格」**

`deltaY` 是「macOS 决定滚多远」，**不是「滚了几格」**。格数就是事件数。

```ts
const notches = unit === WHEEL_NOTCH_DELTA
  ? Math.min(MAX_NOTCHES_PER_EVENT, Math.max(1, |wheelDeltaY| / 120))  // Chromium：±120/格，合并可见
  : 1;                                                                  // WebKit：一事件一格
```

一次 5 事件快滚 = 1.414⁵ ≈ **5.7 倍**（而不是 90 倍）。

### ⚠️ 我连续两轮把测试的符号写反

`wheelZoomFactor` 返回的是**跨度乘数**（放大时 < 1），放大倍数是它的**倒数**。
两轮都因此断言失败——**两次都是实现对、测试错**。
记在这里：写这个模块的断言前，先想清楚「因子是跨度还是倍数」。
