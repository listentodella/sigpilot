# Decoder Performance Self-Test

Stage 1 provides a repeatable release-only baseline for the decoder and graph
path. It uses the same GraphSession, native Saleae backend, sparse transition
view, graph frame conversion, and background decode API used by the desktop
application.

## Run

The representative acceptance command is:

    pnpm perf:self-test -- --scenario 2.5m-i2c-spi --warmups 1 --iterations 10 --output /tmp/sigpilot-perf-2.5m-i2c-spi.json

The full default matrix is:

    pnpm perf:self-test -- --warmups 1 --iterations 10 --output /tmp/sigpilot-perf-full.json

The default matrix contains 250K, 2.5M, and 25M samples, 32 channels, and
UART, I2C, SPI, and I2C+SPI scenarios. A single scenario can be selected with
--scenario 250k-uart, --scenario 2.5m-i2c-spi, or a numeric sample count such
as --scenario 2500000-i2c.

The command refuses debug builds. Run it through cargo run --release or the
pnpm perf:self-test script. --output - or no output path writes JSON to
stdout; the short human summary is written to stderr.

## Fixture and Coverage

The fixture is generated by
sigpilot_core::generate_sample_words_with_count at 25 MHz with all 32 channels
enabled and four bytes per sample. The generated CaptureData is installed into
a real GraphSession, which builds the dense-to-sparse transition index used by
the native decoder.

Reports mark these paths separately:

- packed_dense_input: packed sample storage and GraphSession indexing.
- sparse_transition_index: borrowed sparse transition input sent to the native
  sidecar.
- explicit_sparse_capture_source: intentionally not included in stage 1; this
  is a separate SparseCaptureData source path.

If the sidecar or runtime is unavailable, every requested scenario is emitted
as status "skipped" with the exact reason. Missing runtime must never be
silently converted into a successful result.

## Measurement Semantics

Each scenario performs one first run, one or more warmup runs, and the
requested measured runs. Every run resets analyzer caches while keeping the
capture and waveform edge index, so the decoder is not accidentally measured
as an in-memory cache hit. The first run is the first scenario invocation in
the process and can include sidecar pool initialization; later scenario first
runs are first-after-reset measurements.

Each measured run reports:

- first_graph_result_ready_ms: time until the Rust graph returns a frame
  containing visible analyzer data. This is not browser paint time.
- first_decoded_result_ms: first backend progress or graph result containing
  decoded frames.
- complete_decode_ms: the product background decode path reaching completion,
  including the configured 16 ms polling cadence by default.
- decoder_core_path_ms: a synchronous full GraphSession native decoder path
  after cache reset.
- final_graph_frame_ms: final waveform and analyzer frame conversion after
  complete decode.
- structured stage totals from the existing core and graph timing points.
- request and response IPC byte totals when transport fields are available.

### Stage totals, counts and per-call cost

Stage timings are reported four ways, and the last two are the ones that decide
whether a stage is a bottleneck:

| Metric | Meaning |
| --- | --- |
| `stage.<name>` | total ms spent in that stage during one iteration |
| `stage.<name>.count` | how many times the stage ran in that iteration |
| `stage.<name>.mean_ms` | `total / count` for that iteration, then percentiled across iterations |
| `stage.<name>.call` | percentiles over **every individual call**, pooled across all iterations |
| `stage.<name>.slow_calls` | how many calls exceeded **2x the stage's own median** |
| `stage.<name>.slow_time_share` | what fraction of the stage's total time those slow calls own |

A large total only says a stage ran often. Compare `mean_ms` against the frame
budget to tell "called a lot but cheap" from "genuinely expensive" — for example
`stage.user.graph.analyzer_render` at 7.95 ms total means something very
different at count 1 than at count 200.

`mean_ms` is computed per iteration and then percentiled. Do not derive it as
`total_p50 / count_p50`: those two percentiles can come from different
iterations.

### Why `.call` exists on top of `mean_ms`

`mean_ms` is an average, so it hides a **bimodal** stage — one that alternates
between a cheap and an expensive branch. The concrete case that motivated this:
`analyzer_render` runs twice per iteration, once served from the analyzer cache
and once doing the full window decode. The mean lands between the two and
describes neither.

`stage.<name>.call` pools the raw per-call durations, so `p50` versus `max` shows
the branches directly. For this key the `iterations` field in the summary means
**total calls**, not measured iterations.

### Why `slow_calls` / `slow_time_share` exist on top of `.call`

`p50` and `max` show that two branches exist, but not how the calls are split
between them or whether the slow branch owns the time. That split is what decides
whether the stage is worth optimizing.

`slow_calls` and `slow_time_share` are emitted **only** for stages whose slowest
call exceeds twice their own median — so **the presence of
`stage.<name>.slow_calls` is itself the signal that the stage is bimodal**, and
its absence means it is not. The threshold is relative to each stage's own
median, so no per-stage tuning is needed.

> **Read the share together with the absolute total.** `slow_time_share` is a
> fraction, so a negligible stage can still report a high share — a stage costing
> 0.1 ms total with `slow_time_share = 0.7` is worth nothing. The metric ranks
> *shape*, not *importance*; `stage.<name>` ranks importance.

The report deliberately keeps measurement.ui_visible_result.available=false.
Tauri IPC delivery, React scheduling, and Canvas paint are not observable from
this Rust command and remain a stage 2 measurement decision. It is not replaced
with complete_decode_ms.

Percentiles use nearest rank: ceil(p * n), one-indexed. With ten measured runs,
p50 is the fifth sorted value and p95/p99 are the tenth sorted value.

Peak resident memory is currently marked unavailable because a reliable
cross-platform peak RSS sampler is not part of this stage. The report includes
an estimated current GraphSession allocation total as a separate per-run field;
it must not be interpreted as peak RSS.

## Report Contract

The machine-readable report has schema
pxlogic.performance.decoder-self-test version 1. It includes build profile and
release validity, git revision and dirty state, host OS/architecture, fixture
identity, sample/edge/frame counts, protocol and analyzer counts, first/warm/
measured runs, latency summaries, stage timings, IPC bytes, coverage status,
skipped/failure reasons, and unavailable metric reasons.
